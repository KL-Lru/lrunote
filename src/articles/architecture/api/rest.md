REpresentational State Transfer の略称です.  
Web アプリケーションでリソースを管理/操作する際の事実上の標準となっているアーキテクチャスタイルです.

標準的である割に「REST とはなにか」といえば.

- 「CRUD で HTTP の Semantics に則ってメソッドを割り当てていて...」
- 「リソースで決められた URI でアクセスができて...」

といったことは解答できるものの具体的には答えづらい抽象的なアーキテクチャです.

## 現代における REST

現代における「REST」と呼ばれるアーキテクチャは, おおよその場合 ROA (Resouce Oriented Architecture) をベースとした API アーキテクチャのことを指します.
区別としては REST 自体は考え方, ROA が実現方法, というのが概ね正しいでしょう.

ROA では以下の 4 つの特性を持ちます.

### Addressability

URI を通じて, リソースを指し示します.
裏を返すと, リソースとした情報群には, 必ず URI を割り当てる必要があります.

例えばユーザ ID: 12321 のユーザリソースは /users/12321 などと割り当てて表現します.

また, URI は予測可能なものである必要があります.
ユーザの情報は /users/12321 であるのに対して, 組織の情報は /organizations/detail-by-id/12321 となるような設計は避けるべきでしょう.

### Uniform Interface

情報の操作はすべて HTTP のメソッドを利用して表現します.
重視されるのは統一性であり, 可能な限り同じ用途で利用することだけを要求しています.

以下は 1 つの例です.

| METHOD  | 操作               |
| :------ | :----------------- |
| GET     | 取得               |
| QUERY   | 検索               |
| POST    | 作成               |
| PUT     | 更新 (置換)        |
| PATCH   | 更新 (部分)        |
| DELETE  | 削除               |
| HEAD    | メタデータ取得     |
| OPTIONS | 通信オプション取得 |

QUERY は　[RFC 10008](https://datatracker.ietf.org/doc/html/rfc10008) で定義された比較的新しい HTTP メソッドです.
従来 GET ではペイロードを持てずクエリパラメータで送付するものとなっており, 複雑なデータや長さ制限にかかりうるものは POST などで代替されていました. QUERY が新たに追加されたことで, この領域の役目を担えるようになりました.

個人的な考えで述べるなら以下の通りに対応されるのが最良と考えています.

- 検索
  - 利用者の Proxy 環境, LB や WAF 等の対応状況を気にしないなら, 新たに誕生した QUERY がよい
  - パラメータ数が少ないのであれば GET がよい
  - パラメータ数が多いのであれば POST がよい
- 作成
  - クライアントサイドで ID 値を定めたい + 冪等でありたい + それをシステム全体で行いたい場合のみ PUT がよい
  - それ以外のほとんどの場合においては POST がよい

### Stateless

各リクエストにはそのリクエストを処理するために必要な情報をすべて含めます.
特定のリクエストでサーバ側にクライアントの状態を格納し, それを元に別のリクエストが処理するようなことは許容されていません.

例えば操作中のテナントを変更する API をリクエストすると, それ以後のリクエストで作成されるユーザのひも付きが変わるようなものは Stateless ではありません.
テナント切り替えなどはなく, ユーザを作成する際にテナント ID を指定して作成するようなものであれば Stateless となります.

この性質については, 単にサーバ側に状態を持ってはならないという話ではなく, リソース等のデータや時間経過での変動などのサーバ側で管理されている情報群に関しては言及していません.
このため, 特定のリソースの作成には別のリソースの作成が必要といった依存や, 有効期限を属性として持つリソースの有効残り時間といった変動する情報はこれに反しません.

リクエスト時の Session Cookie や Access token は単に認証/認可の話であり, この要求事項とは分けて考えるべき要素でしょう.
認証認可においてはクライアントが誰で, どのリクエストが可能な権限を有していて, レートリミットはどれだけ残っているか, といった情報の管理は必要不可欠です.
これらはクライアントの状態に当たりますが, 現代においてはこういった情報の管理が含まれていようとも, 多くの場合 REST と呼ばれます.

### Connectivity

リソースには, 別のリソースの URI を含めることができます.

例えばユーザの情報を取得した際には, そのテナント情報を取得するための URI を含めてもよいでしょう.
必要ならここから情報を取得せよ, という情報取得のための道しるべとなります.

この性質についても, 現代においては満たしていない API も多くの場合は REST と呼ばれます.
他の特性を満たし, 関連するリンクを含めるような API は HATEOAS (Hypermedia As The Engine Of Application State) と呼ばれます.

個人的にはこの性質の必要性には懐疑的です.
現代においては多くの場合 API はドキュメントとともに公開され, 利用者はどこに何のリクエストを送付すれば情報が得られるかを網羅的に知ることができます.
原論でも触れられている領域ですが, 大元は HTML 等のレスポンスを返す場合において, 関連リンクを配備することを要求するものだったのではないかと考えています.

## 原論

REST という考え方の原論は Fielding 氏の論文[^origin]によって提唱されたアーキテクチャスタイルにあります.
この原論で提唱されているアーキテクチャでは, よく聞く 4 原則とは異なる 6 つの制約が挙げられています.

この論文が提起された 2000 年当時は, 未だ JSON などの表現方法は存在しておらず, おおよその想定が HTML ベースであろう点には注意が必要です.

### Client-Server

クライアントとサーバが分離されており, 独立して改修 / 進化が可能になっていることを要請します.  
主として述べるべきは関心の分離であり, 今となってはほとんどの一般的なシステムで見られる方式です.

### Stateless

クライアントからサーバへのリクエストが, それ単体で必要なすべての情報を含んでいることを要請します.  
サーバはセッションの状態管理をすることなく, セッションはすべてクライアントサイドで管理します.

リクエスト間でリソース利用の管理などを行う必要がなくなるため, スケーラビリティは高く, 可観測性も向上します.  
代償として, 必要な情報はすべてのリクエスト/レスポンスで送付する必要があるため, この点でのスループットは低下します.

### Cache

各レスポンスがキャッシュ可能かどうかを明示的にラベル付けすることを要請します.

レスポンスキャッシュを利用することでパフォーマンスの向上が図れますが, キャッシュとサーバの実データの乖離の発生を避けられるよう, 適切に可否を判断する必要があります.

### Uniform Interface

REST では統一的なインターフェースを重視することを特徴としており, 次の 4 つの制約を満たせるように定義されています.

#### Identification of Resources

REST で提供される対象となる概念は, すべて特定のリソースとしてマッピングされていることを要請します.
また, どのリソースを操作や取得の対象とするのかを識別可能となるよう, リソース識別子が利用されます.
通常リソース識別子には URI などが用いられます.

#### Manipulation of Resources through Representations

クライアント <-> サーバ間などの間のやり取りは, 何らかのリソースを表現するものを用いてやり取りすることを要請します.
HTML ドキュメント自体や, JSON, 画像ファイルなどがこれに当たります.

#### Self-descriptive Message

レスポンスの表現にはメディアタイプなどのメタデータも含まれ, 受信者がどのように処理を行わなければならないのかなどを自己言及的に指定するものを含むことを要請します.  
Content-Type などがこれに当たるでしょう.

#### Hypermedia as The Engine of Application State

レスポンスの表現に含まれている次の状態への遷移を選択することで, アプリケーションの状態を進ませることができることを要請します.  

おそらく現代で言うところの単なるリンク遷移や Form の POST などが行えることを要請しているものです.
現代の JSON などでの API でいうところの HATEOAS に当たります.

### Layered System

システムが複数層のレイヤーにまたがることを許容します.
システムを構成する要素はその相手との疎通の間にある詳細までを知る必要はありません.

現代で言うところのロードバランサやプロキシがこれに当たるでしょう.
クライアントがリクエストする際に, LB があるか, などを識別する必要はありません.

### Code-On-Demand

クライアントに対してコード実行を許容します.
唯一の optional な要請です.

現代で言うところの HTML に乗っている JavaScript のようなものです.


[^origin]: [Architectural Styles and the Design of Network-based Software Architectures](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm)
